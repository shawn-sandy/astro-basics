Executive Summary

Six reviewers — Product Manager, Lead Developer, UX Designer, Lead Frontend Engineer, Accessibility Expert, and Security Expert — assessed the plan in parallel. All six returned approve with changes; none were unavailable. The core approach (native Popover API, no JavaScript, disclosure semantics over ARIA menu roles) was endorsed without dissent.

The original draft leaned on two mechanisms that are factually wrong. The Lead Developer disproved both empirically in Chrome, and a third finding made one verification command unrunnable. All revisions have been applied to the source plan.

Approve with revisions

The approach is sound and unanimously endorsed; the revisions were mechanical corrections rather than a change of direction. Five blocking items have been applied to the plan, along with the non-blocking improvements. Three genuine product decisions are recorded as Unresolved Questions for the plan owner rather than guessed at.

Revised Objective

Replace the inline navigation link list with a hamburger button that opens a native HTML popover panel (the popover="auto" attribute plus a popovertarget button) at all screen sizes, matching the reference screenshot's top-right dropdown menu.

Verified Corrections

Original claim What is actually true Applied fix
Style the open state with [aria-expanded="true"] — browsers set that attribute on popover invokers automatically. False. The expanded state is an implicit accessibility-tree mapping, not a serialized DOM attribute. Verified in Chrome: hasAriaExpandedAttr: false, the rule never applied, and getByRole('button', { expanded: true }).count() returned 0. Use nav:has(> [popover]:popover-open) button[popovertarget], which did match in the same test.
Wrap the links in a <div popover>. The attribute's invalid-value default is manual, and manual popovers have no light dismiss and no Esc close — the two behaviors the entire no-JavaScript rationale depends on. A stray popover={true} breaks it with no error. Write popover="auto" explicitly and assert it in the unit test.
Verify with npm run sass. npm run sass is a --watch watcher that never terminates. No other repo command compiles SCSS — npm run build does not — so a forgotten recompile ships unstyled with every test green. Add a one-shot sass:build script and verify with npm run sass:build && npm run lint:styles.
Unsupported browsers render the panel content inline — acceptable degradation. Unsupported browsers do not hide [popover] at all. Combined with the planned position: fixed, the menu renders as a permanently-open overlay beside a hamburger button that does nothing when activated. Add a @supports not selector(:popover-open) block that hides the button and renders the links as a static inline row.
No mention of existing base styles. _base.scss:12-24 uses a direct-child combinator (body > nav > ul) that silently stops matching once the list moves inside the popover div. Repair the selector as part of Step 4, and reset the UA popover box (inset: auto; margin: 0) before applying offsets.

Revised Steps

  1. Establish a green baseline: npm install, Playwright browser install, and a passing pre-change test run. The worktree has no node_modules and the local Playwright cache is version-mismatched.
  2. Add the one-shot sass:build script to package.json.
  3. Restructure Navigation.astro: exported Props, brand link, hamburger button with an aria-hidden inline SVG, popover="auto" panel with a namespaced id, and <nav aria-label="Primary">.
  4. Create _navigation.scss, register it, repair _base.scss, and style the bar, the 44×44px button, and the clamped top-right panel using existing --card-* and --space-11 tokens.
  5. Add the @supports fallback guard.
  6. Add a unit test via experimental_AstroContainer for the markup contract.
  7. Add the Playwright spec: open/close, Esc with focus restoration, light dismiss, keyboard access, 44px bounding box, reduced motion, axe-core scan, and a negative-authorization assertion.
  8. Re-run the home suites and verify no authenticated markup reaches dist/.
  9. Document the pattern in project docs and the Starlight guide.

Acceptance Criteria

Fourteen criteria, up from nine. New additions cover explicit popover="auto", focus restoration on close, the panel never covering the login control (WCAG 2.2 SC 2.4.11), no horizontal scroll at 320px (SC 1.4.10), the no-popover fallback appearance, zero authenticated link leakage to anonymous visitors, no new dependencies, and a full lint/type/test gate.

Unresolved Questions

Three decisions belong to the plan owner and were recorded rather than guessed:

  • Dashboard and Profile placement. Four reviewers flagged that the login slot carries userId-gated links, so signed-in users still see an inline link row — backwards for a cleanup feature. Move them into the panel, or keep them in the bar?
  • Library-consumer slot contract. Navigation.astro is a public export; relocating its default slot inside [popover] changes where consumer content renders. Breaking change with a version bump, or keep the slot outside the panel?
  • Sticky bar. Popovers are viewport-fixed and do not close on scroll, so the panel detaches from the hamburger as the page scrolls. Make the bar sticky, or accept it?

Reviewer Conflicts

Topic Conflict Resolution
Panel positioning UX wanted position: absolute anchored to a relative nav so the panel emerges from its trigger; Frontend and Lead Dev assumed fixed with an explicit inset reset. Keep fixed. Top-layer elements position against the viewport and ignore ancestor positioning contexts, so absolute does not produce the anchoring UX wants. The legitimate concern — a panel snapping to the viewport edge while the button sits inset — is addressed by deriving the right offset from the same content-width constraint the bar uses.
Success metrics PM asked for metrics, an A/B test, and a rollout plan; no other reviewer raised measurement. Partially adopt. On a low-traffic demonstration site an A/B harness costs more than the change it measures. Business rationale and an explicit git revert rollback note were added; the A/B test was not.
Security scope Security wanted middleware.ts and netlify.toml amended inside this plan. Split. The two items belonging to this change — the non-goal statement and the negative-authorization test — became steps. The middleware and header changes are real but independent, so they became Next Steps prompts rather than scope creep.
JS shim vs. no-JavaScript criterion A11y asked whether a minimal ARIA shim would be acceptable if an engine fails to announce the expanded state — which would violate an acceptance criterion the user set. Left unresolved by design, as an open question for the user rather than silently relaxing their criterion.
Panel Review (full report)

Highest-Risk Issues

  1. [Lead Dev] [aria-expanded="true"] is a no-op — empirically verified false in Chrome. The open-state criterion was untestable and the styling would silently never apply.
  2. [Lead Dev] A bare popover attribute can resolve to manual, silently killing light dismiss and Esc.
  3. [UX / Frontend / A11y] The stated graceful degradation was actually a broken header — a permanently-open fixed overlay beside a dead button.
  4. [Security] Auth-gated markup relocation with no non-goal statement (CWE-602) and no verification that prerendered routes stay clean (CWE-524).
  5. [Lead Dev] npm run sass never terminates, and no other repo command compiles SCSS.

Blocking Issues

  • [Lead Dev] The open-state CSS hook must change to nav:has(> [popover]:popover-open) button[popovertarget].
  • [Lead Dev] popover="auto" must be explicit.
  • [Lead Dev] A one-shot SCSS build script must exist.
  • [Frontend] _base.scss:12-24 must be repaired.
  • [UX / A11y] The @supports fallback guard is required for the degradation claim to hold.

Accessibility Requirements

  • Assert focus returns to the invoker after Esc (SC 2.4.3); test per engine.
  • Guarantee the panel never overlaps the login control while both are in the focus path (WCAG 2.2 SC 2.4.11).
  • Clamp panel width to min(16rem, calc(100vw - 2rem)); verify no horizontal scroll at 320px (SC 1.4.10).
  • Automate reduced motion with page.emulateMedia({ reducedMotion: 'reduce' }).
  • Add an axe-core scan of the open panel against WCAG 2.2 AA.
  • aria-hidden="true" focusable="false" on the inline SVG.
  • aria-label="Primary" on the <nav> to disambiguate from the unlabeled landmarks in Pagination.astro and AstroPages.astro (SC 1.3.1).
  • Name contrast-checked tokens: ≥4.5:1 for panel link text (SC 1.4.3), ≥3:1 for button border and icon (SC 1.4.11).
  • Reuse the repo's outline: 2px solid; outline-offset: 2px focus convention (SC 2.4.7).
  • Hide the hamburger in the no-popover fallback so nobody activates a dead button.
  • Corrected citation: WCAG 2.2 SC 2.5.8 Target Size (Minimum), 24×24 CSS px — the plan's original "WCAG 2.1 AA target size" does not exist; 2.1's criterion is AAA.

Security Requirements

  • State that the popover is presentational and must never gate authenticated content (CWE-602).
  • Negative-authorization E2E assertion: an anonymous visitor sees zero Dashboard and Profile links.
  • Build-output check: grep -rl 'href="/dashboard"' dist/ must return empty after npm run build (CWE-524, OWASP A01:2021).
  • Enforce the no-new-dependency intent with a lockfile diff check (OWASP A06:2021).
  • Namespace the popover id to survive a duplicate-id collision from MDX-authored raw HTML.
  • Require the icon be a literal inline <svg>, never set:html (CWE-79).
  • Deferred to Next Steps: /profile middleware coverage (OWASP A01:2021) and baseline framing headers in netlify.toml (OWASP A05:2021).

Frontend Implementation Considerations

  • Repair body > nav > ul; reset inset: auto; margin: 0 before applying offsets.
  • Use --card-* tokens, --space-11 (44px), and --transition-duration-150 rather than literals.
  • Flatten selectors to respect stylelint's max-nesting-depth: 4 and selector-max-compound-selectors: 4.
  • Reset the acss descendant rules (nav ul > li { min-height: 100% }) that follow the list into the panel.
  • CI runs Chromium only — cross-engine claims need a local three-engine run before merge.
  • A fade-out, if ever added, needs transition-behavior: allow-discrete.

Technical Feasibility Concerns

The worktree has no node_modules, and the local Playwright browser cache is version-mismatched (@playwright/test 1.59.1 wants chromium_headless_shell-1217; the cache holds -1234). Combined with the recorded note about Chromium install hangs, this is the plan's highest delivery risk, now addressed by an explicit baseline step. The two dark-mode systems conflict — _design-tokens.scss keys off prefers-color-scheme while acss keys off [data-theme="dark"], which Base.astro never sets — so the dark-mode verification could not pass honestly and moved to Next Steps.
