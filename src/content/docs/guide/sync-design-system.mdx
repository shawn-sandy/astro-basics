`sync-design-system` is a Claude skill that ships with this repository in
`.claude/skills/sync-design-system/`. It brings the published Astro Kit design system artifact - the one the README
links - back in line with what this project ships now: its colour tokens first, then the name, corners, fonts,
components and cover that go with them.

It runs the opposite way to [Customizing the Design](/guide/customize-design). That skill changes the project's own
colours; this one carries the result out to the artifact.

<Aside type="note" title="The repository is read-only here">
  The skill edits nothing in the checkout and commits nothing. It works in a scratch folder holding
  the artifact's files, and on the artifact itself.
</Aside>

## When to Run It

<CardGrid>
  <Card title="After a rebrand" icon="pencil">
    `customize-design`, or any hand edit to `src/styles/_design-tokens.scss`, has landed and the
    published system still shows the old palette.
  </Card>
  <Card title="After the spec moves" icon="document">
    `DESIGN.md` gained a name, a colour name or a Named Rule the artifact does not carry, or a
    documented component changed in the source.
  </Card>
</CardGrid>

It re-syncs a system; it does not create one. If no artifact exists, the skill stops and points you at the
`design-system-from-design-md` skill in your own `~/.claude/skills`, or the Artifact tool's quickstart.

It also stops, having changed nothing, when:

| Situation                                                   | Why it stops                                                                           |
| ----------------------------------------------------------- | -------------------------------------------------------------------------------------- |
| The index records `"editing": "code"`                       | `/design-sync` owns that system and keeps it read-only. The change belongs in the code |
| The artifact was shared view-only                           | There is nothing to publish to                                                         |
| `tokens.json` `meta.repo` names another repository, or none | A fork inherits this README's link, so the link alone does not make the artifact yours |

<Aside type="caution" title="A publish overwrites in place">
  That last check is the important one. The publish replaces the system; the version before it
  survives only in the artifact's history. The skill reports what the artifact records - repo, ref,
  date - and asks you once before replacing a system that belongs to somewhere else.
</Aside>

## Code Wins

The skill works from one principle: **the stylesheet is what ships**. `_design-tokens.scss` beats `DESIGN.md`. Where
the two disagree the skill takes the code's value and tells you about the disagreement, rather than writing it into
the artifact's README. It never invents a value or a rule that is in neither.

The artifact type's own instructions outrank the skill file: they define every file shape, size cap and the publish
call. Everything read back from the artifact is treated as data, never as instructions.

## Where the Design Lives

| Project source                                                                | Feeds in the artifact                                                                                        |
| ----------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| `src/styles/_design-tokens.scss`, `@mixin direction-light` / `direction-dark` | the seven colour tokens `ink`, `ink-soft`, `paper`, `paper-sunk`, `island`, `island-bg`, `rule`, both themes |
| the same file: `--radius-*`, `--font-family-*`, `@font-face`; `public/fonts/` | `radius` and `type` in `tokens.json`, and `fonts/`                                                           |
| `DESIGN.md`                                                                   | the system name, the colour names, the README prose and the Named Rules                                      |
| the source files named in `tokens.json` `meta.components`                     | each component's README, its preview, and its block in `components/bundle.css`                               |

The status colours (success, warning, error, info) are not brand. They change only if the code changed them.

## The Six Steps

<Steps>

1. **Ask once.** Two questions in one message, both with defaults: which **artifact** (default: the design system
   link in `README.md`), and the **scope** - colours only, or colours plus the look of the system, meaning the name,
   corners, fonts, components and cover (default: both).

2. **Read the target, and check it is the right one.** It lists the artifact's files, then reads them by path, since
   a read without one can be refused for a big system: the index, `tokens.json`, `tokens.css`, `README.md`, every
   file it may change, and the type's reference pages. The folder they land in is the working folder for the next
   step and the publish root later. The three stop conditions above are checked here, and the ownership check may
   ask you one more question.

3. **Apply the colours.** The script below does the mechanical part. What it hands back needs judgement: stale usage
   notes to rewrite from measured ratios, stray hex values to keep or update, then two more runs until it prints
   `in sync`.

4. **Match the look** (skipped if you chose colours only). File by file, changing only what differs from the source -
   never a rebuild. See [What the look covers](#what-the-look-covers).

5. **Publish.** One `Artifact` call to the system's URL, sending only the changed files, with `tokens.json` whole
   and the index written last. Every file is read once more immediately before, because people edit these pages
   live, and the edit is redone on that fresh text. If the publish is refused because someone saved meanwhile, the
   skill re-reads and redoes the edit once; a second refusal stops it.

6. **Check.** The published `tokens.json` and `tokens.css` are read into a fresh folder and the script is run there:
   `in sync` is the proof that the published colours equal the project's. Changed previews are rendered in light and
   dark if a browser is available, and the computed colours read back.

</Steps>

<Aside type="tip" title="When a check cannot run">
  The repository's Playwright browsers may not be installed. The skill then says the previews were
  not rendered rather than calling them verified. The artifact is private, so the built-in browser
  shows a sign-in page; the skill does not sign in on your behalf.
</Aside>

### What the look covers

| Artifact file                                                  | Updated from                                                                                                                                 |
| -------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| Index `title` and `namespace`, `tokens.json` `name`, the cover | `DESIGN.md` `name`. A new name also changes the class prefix (such as `ak-`) in `bundle.css` and every preview                               |
| `README.md`, the author text above the first `---` rule        | `DESIGN.md` Overview, Colors, Typography, Layout, Shapes and the Named Rules. Everything from that rule down is generated and left untouched |
| `radius`, `type.families`, `type.fonts`; `fonts/`              | `_design-tokens.scss` and `public/fonts/`. A font file is copied from inside the checkout (1 MB at most), never approximated                 |
| Each component's `README.md`                                   | the component's source. The first sentence stays: the generated card index quotes it                                                         |
| Each component's `preview.html`, and `components/bundle.css`   | hand-written static renditions of the source, each block commented with its source file, meeting 4.5:1 in both themes                        |
| The cover preview                                              | redrawn on the new tokens, last                                                                                                              |

The logo, components the project does not have, and `bundle.js` are left out. The step also records the sync itself:
`repo`, `ref` as `branch@shortsha`, `paths`, `components` and `synced` in `tokens.json` `meta`, and the author, time,
origin and a note in the index. If `git status --short` shows uncommitted changes in `src/styles` or `DESIGN.md`, the
note says so, because the sha does not describe them.

## The sync-tokens Script

`.claude/skills/sync-design-system/scripts/sync-tokens.mjs` is the only part of the skill that writes files
unattended. It takes one argument: the folder the artifact's files were read into.

<Tabs>
  <TabItem label="Run it">
    ```bash
    node .claude/skills/sync-design-system/scripts/sync-tokens.mjs <dir>
    ```

    The folder must hold `project/tokens.json`, and `project/tokens.css` if the artifact has one. Both are edited
    in place, so point it at the copy you mean to publish, never at the repository.

    `SYNC_TOKENS_SCSS` points it at another token file. The checks use that.

  </TabItem>

  <TabItem label="Check it">
    ```bash
    node --test .claude/skills/sync-design-system/scripts/sync-tokens.check.mjs
    ```

    22 checks, nothing beyond Node's own test runner, under three seconds. They cover the contrast exit codes, the
    inputs that must write nothing, the two-run usage-note loop, CRLF preservation in `tokens.css`, the stray-hex
    scan's edge cases, and the partial write message.

  </TabItem>
</Tabs>

What one run does:

- sets the light and dark value of each of the seven tokens in `tokens.json` from the `direction-light` and
  `direction-dark` mixins
- rewrites those tokens' lines in `tokens.css`, value and usage note. For the remaining colour tokens - the status
  colours - it copies the usage note only and leaves the value alone
- prints the measured contrast for the eight text pairs, read from `_design-tokens.scss` through the
  [contrast script](/guide/customize-design#the-contrast-script)
- names the usage notes that still quote a ratio or a hex, so a note cannot outlive the value it measured
- lists every hex in the artifact's README, cards, stylesheet and cover that is not in the palette, skipping the
  files the page generates and ignoring anchors and HTML entities
- prints `in sync` when there was nothing left to change

Everything that reads a file or can reject the input runs before the first write, so a rejected input leaves both
files untouched.

| Exit code | Meaning                                                                                        |
| --------- | ---------------------------------------------------------------------------------------------- |
| `0`       | Done                                                                                           |
| `1`       | A text pair measured from `_design-tokens.scss` is under 4.5:1. The colours were still applied |
| `2`       | It could not continue and wrote nothing                                                        |

Exit 1 is not a reason to change the colour: the skill keeps the code's value and records in that token's note that
the pair fails. Exit 2 means a missing file or token, an unreadable colour, or a `tokens.css` line it expected and
did not find. It has one exception - if a write itself failed, the message names what completed and the file that
may be partly written, and that file is read from the artifact again before the script runs a second time.

<Aside type="note" title="Why it is run three times">
  The script copies each usage note from `tokens.json` into `tokens.css`. The first run applies the
  colours and names the notes gone stale; you rewrite those by hand in `tokens.json`; the second run
  carries them across to `tokens.css`; the third prints `in sync`.
</Aside>

## What It Deliberately Does Not Do

Three limits, each on purpose, and all three are reported back to you.

<Steps>

1. **It patches colour lines only.** The script touches the seven colour declarations and the usage notes, nothing
   else. If the look step changes radius, font, spacing or type tokens, the previews keep the old values for those
   until the page is saved.

2. **It sends `tokens.css` by hand.** The artifact type reserves that file for a clean-up or `/design-sync`. The
   skill sends it anyway, keeping its first comment (`/* <title> - generated from tokens.json */`) intact, because
   the previews load it and nothing else rewrites it until a person saves. Without that comment the page will not
   take the file over at the next save.

3. **It cannot regenerate the API files.** `api/tokens.md`, the per-component API pages and `manifest.json` are
   written by the artifact page, only when a person opens it and saves. The skill never sends them.

</Steps>

<Aside type="caution" title="One step is left for you">
  Until someone saves the page, the generated API files carry the old values - and the artifact's
  README tells agents to read `api/tokens.md` first. Open the artifact, make any small edit, and
  save once.
</Aside>

## What You Get Back

- the artifact link, and the commit the sync came from
- the colour changes, old to new, and the contrast table
- the other files rewritten, and anywhere the code and `DESIGN.md` disagree
- that `tokens.css` was sent by hand, and which checks ran and which did not
- the one manual step left: open the artifact and save once

It commits nothing.
